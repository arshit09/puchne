Five places code runs

Every arrow is a message, a storage write, or a script injection — never a function call.

Why a worker in the middle?
Only the service worker can open tabs, inject scripts and read chrome.permissions. A content script has none of those, and the popup dies the instant you click away — so anything that must outlive the click lives here.
One panel, three surfaces?
PuchnePromptPanel is a single class rendered into the popup, the Chrome side panel and an in-page overlay. Each host supplies only what is genuinely its own — a backdrop, a theme toggle, a layout mode.
Why type instead of call an API?
No API keys, no accounts, no per-token cost — it drives the sessions you are already signed into. The price is fragility: when a site redesigns its composer, a CSS selector in the registry has to change.

    The permission model

    Granted at install — but zero websites
    storage, tabs, scripting, activeTab, tabGroups, webNavigation, sidePanel, contextMenus, declarativeNetRequestWithHostAccess.

    Websites: none. Not one.
    Asked for, one site at a time
    Every AI host sits in optional_host_permissions and is requested the first time you switch that tool on. Chrome shows its own dialog; Puchne only opens the window that can legally ask. Withdraw any of them from Settings › AI Tools at any time.
    What that costs the code
    A site can be granted or revoked at any moment, so three things are re-derived on every change: the local.grantedOrigins mirror (content scripts have no chrome.permissions API), the dynamically registered puchne-service-hosts script, and any send parked mid-flight. That is syncHostAccess() — and it runs on every worker startup, because permissions can be revoked from Chrome's own UI while the worker is asleep.
